# Bug: Command injection in gitLastTouchIso() via unescaped shell string

## Symptom

`_shared/a1-tools.cjs` builds a shell command string for `git log` by
`JSON.stringify`-quoting each argument and joining with spaces, then passing
the result to `execSync`. `JSON.stringify` only adds double quotes — it does
not neutralize shell command-substitution syntax. A path containing
`$(...)` or backticks is executed by the shell even though it sits inside
double quotes.

## Reproduction Steps

1. Craft a spec file whose body contains an inline-code file anchor with a
   shell metacharacter payload, e.g. `` `a/$(touch /tmp/pwned).md` ``.
2. Run `a1-tools reconcile parse-spec <spec-path>` — the anchor is extracted
   by `extractAnchorsFromSpec`/`classifyAnchor`, whose only gate is "contains
   `/` and ends with a known extension"; shell metacharacters are not
   filtered.
3. The anchor ref flows into `gitLastTouchIso()`, which shells out via
   `execSync(\`git ${args.map(a => JSON.stringify(a)).join(' ')}\`, ...)`.
4. Observed: `/tmp/pwned` is created — arbitrary command execution confirmed
   during the quality-analysis security lane (2026-07-12).

Expected: the crafted path is treated as a literal, inert file path (git
reports "no such path" or similar) — no shell execution occurs.
Actual: the `$(...)` payload executes as a shell command.

## Impact

`a1-tools reconcile parse-spec` is designed to run against specs, including
specs generated by `a1-modernize`/`a1-rafael` from an *analyzed, potentially
untrusted* target codebase. A hostile file name in the target repo can
surface verbatim as an inline-code anchor in the generated spec, giving that
untrusted repository content an path to arbitrary command execution on the
machine running a1-tools. This is the single security-relevant finding in
the 2026-07-12 quality audit (0 BLOCKER, 8 MAJOR, 7 MINOR overall) but is a
BLOCKER on its own merits (confirmed RCE).

## Diagnosis (Phase 02 — filled by Falk)

**Hypothesis / Root Cause:** `gitLastTouchIso()` constructs a shell command
line by string-interpolating `JSON.stringify`-quoted arguments into a
template string passed to `execSync`. `JSON.stringify` escapes only
characters that are special to JSON string literals (quotes, backslashes,
control chars) — it has no awareness of POSIX shell syntax. Inside a
double-quoted shell token, `$(...)`, backticks, and `$VAR` all still
expand/execute. Any attacker-influenced string that reaches this function
as a `git log` path argument achieves arbitrary command execution.
**This is not an isolated bug — it is one instance of a repo-wide
anti-pattern.** A sibling-site sweep of `_shared/` found four more shell
string-built `execSync` calls with the same class of vulnerability.

**Evidence — full site list (verified against worktree
`/Users/rob/code/a1-worktrees/fix-cmd-injection-git-helper` @ ed92031):**

1. `_shared/a1-tools.cjs:4271` (`gitLastTouchIso`, fn spans 4263–4280) —
   `execSync(\`git ${args.map((a) => JSON.stringify(a)).join(' ')}\`, { cwd: repoPath, ... })`.
   Call chain: `cmdReconcileParseSpec` (4282) → anchor extraction (gate:
   "contains `/` and ends with known extension", no metacharacter
   filtering) → `relRefs` → `gitLastTouchIso(t.repo_path, fileRefs)` (4336).
   **Empirically confirmed RCE** (payload executed, file created) in the
   2026-07-12 security-review lane. Originally reported site.
2. `_shared/a1-tools.cjs:6294` (`phantomDefaultSince`) —
   `execSync(\`git -C "${repoPath}" log -1 --format=%H -- "${rel}"\`)`.
   `repoPath` is user-controlled via CLI flag `--repo-path <abs>` (line
   6371) → injection via a crafted repo-path argument.
3. `_shared/a1-tools.cjs:6304` (`phantomDefaultSince`) —
   `execSync(\`git -C "${repoPath}" rev-parse "${last}^"\`)`. Same
   `repoPath` vector; `last` is a git commit hash (lower risk on its own).
4. `_shared/a1-tools.cjs:6324` (`phantomCollectDiff`) —
   `execSync(\`git -C "${repoPath}" diff --name-only ${since}..HEAD\`)`.
   BOTH `repoPath` AND `since` are user-controlled (`--since <git-ref>`,
   line 6372); `since` is interpolated **completely unquoted** — cleanest
   injection of the set (e.g. `--since '$(touch /tmp/pwned)'`).
5. `_shared/a1-tools.cjs:6334` (same function) —
   `execSync(\`git -C "${repoPath}" diff ${since}..HEAD\`)` — same two
   vectors as #4.
6. `_shared/a1-tools.cjs:3677` — `find "${root}" ... | grep ...` shell
   pipeline; `root` is an analysis target directory. Command-substitution
   in `root` would execute. Lower priority but same trust boundary (target
   dirs can come from analyzing an untrusted codebase).

Confirmed **safe / no action needed**: `a1-tools.cjs:1195/1200/1205`,
`_shared/lib/io.cjs:44` (fixed literal git commands, no interpolation).
Confirmed **good example to mirror**: `_shared/lib/worktree-registry.cjs:52`
— `execFileSync('git', ['-C', repoRoot, ...args], {...})`, the safe
argv-array form (no shell involved).

**Confidence:** high (root-cause site empirically reproduced; sibling sites
found by direct pattern sweep and manual line-by-line confirmation of the
same string-interpolation anti-pattern; worktree-registry counter-example
independently verified).

**Recommended code agent:** a1-walter-web-developer (Node.js CLI codebase;
no project-specific backend agent configured for a1-specforge).

**Suggested fix approach:** This is **not** a single-spot patch — convert
**all five vulnerable sites** (4271, 6294, 6304, 6324, 6334) from
string-built `execSync` to `execFileSync('git', [argv...], opts)`, plus the
lower-priority `find`/`grep` pipeline at 3677. Best approach: route every
git invocation through the existing safe `worktree-registry.cjs` `git()`
helper (argv-array `execFileSync`) instead of re-implementing per call
site, so there is one audited exec path repo-wide. For 3677, replace the
shell pipeline with `execFileSync('find', [...args])` and do the
node_modules/.git filtering in JS. As defense-in-depth, also reject/strip
refs containing shell metacharacters (`$`, backtick, `;`, `|`, `&`, `<`,
`>`, `(`, `)`, newline) at the CLI argument-parsing boundary, so any future
exec-call site added elsewhere fails safe too. Regression tests: one per
injection vector (hostile anchor via `reconcile parse-spec`, hostile
`--since`, hostile `--repo-path`) asserting no side effect occurs and the
literal string is passed through as an inert path/ref.

## Fix Plan (Phase 03 — filled by code agent)

**Approach:** Converted all 6 shell string-built `execSync` call sites in
`_shared/a1-tools.cjs` to argv-array `execFileSync` via a new shared helper
`_shared/lib/git-safe.cjs` (`gitSafe()` + `assertNoShellMetachar()`),
mirroring the safe pattern already used in `worktree-registry.cjs`. Added
defense-in-depth shell-metacharacter rejection at the `--repo-path`/`--since`
CLI parsing boundary in `cmdPhantomCheck`.
**Files to change:** `_shared/a1-tools.cjs` (modified, 6 call sites),
`_shared/lib/git-safe.cjs` (new), `_test-fixtures/a1-cmd-injection/run.sh` (new)
**Regression test added:** yes — `_test-fixtures/a1-cmd-injection/run.sh`, 7
assertions covering all 3 named vectors (hostile inline-code anchor via
`reconcile parse-spec`, hostile `--repo-path`, hostile `--since`) plus one
control case. Verified red→green by the code agent (stashed the fix,
reran against vulnerable code — all 3 vectors reproduced actual RCE with
marker files created on disk; restored the fix — all 7 green).
**Risk:** Low. Behavior-preserving for all non-hostile inputs (git output
format unchanged); the CLI-boundary metachar rejection is new-surface but
only rejects inputs that were already unsafe. Two pre-existing fixtures
(`a1-reconcile` single-pass/single-missing) regenerate timestamped output
files as a known, unrelated side effect of running the suite — not part of
this change.
