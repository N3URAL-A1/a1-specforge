# Wave Plan — Scroll Motion Redesign

> Spec: `002-scroll-motion-redesign` · Project: `a1-office-landing` · Size: M · 10 FRs / 6 SCs
> Stack: Next.js 16 App Router, React 19, Tailwind 4, pnpm. Pure frontend marketing site — no DB, no API routes, no auth, no existing test framework. Follow-up redesign on the post-001 `main` codebase (all spec-001 motion infrastructure present under `components/motion/` and `lib/motion/`).

## Planning notes (read before executing)

- **This is a hot-codebase revision, not greenfield.** Spec 001 shipped and merged; every building block the new effects compose (`LenisProvider`, `MotionGateProvider`, `useMotionGate`, `useIsDesktop`, `useReducedMotion`, `useLenis`, `SectionReveal`) is already real and located. Read the current `components/motion/*` and `lib/motion/*` before touching anything — do not re-invent hooks that exist.
- **Removal must relocate the grid shell (edge case, spec line 141).** The `md:grid-cols-3` grid container currently lives INSIDE `ValueGalleryMotion` (`ValueGalleryMotion.tsx:65` — `className="mx-auto grid max-w-5xl gap-5 md:grid-cols-3"`), not in `ValueSection`. `ValueSection.tsx:44-65` passes its `.map()`'d cards as `children` into it. When `ValueGalleryMotion` is deleted, this grid shell (and card 0's `md:col-span-2`, which depends on being a direct grid child) MUST move back into `ValueSection` (or the Wave 2 stagger wrapper), or the bento layout breaks. This is the single load-bearing structural detail of the removal.
- **No orphaned code after removal (FR-002, edge case spec line 57).** After `ValueGalleryMotion` is gone, `lib/motion/use-scroll-progress.ts` has ONE remaining consumer (verified: only `ValueGalleryMotion` imports it; `use-scroll-state.ts:21` only references it in a doc comment, not in code). Either the Wave 2 parallax generalizes/reuses it, or it must be deleted — no dead hook left behind. `lib/motion/value-gallery-shifts.ts` has no consumer except `ValueGalleryMotion` and is a hard delete. Doc-comment references to `ValueGalleryMotion` in `use-reduced-motion.ts:11`, `motion-gate-context.ts:29`, `use-scroll-progress.ts` must be updated or the file deleted so no comment points at a non-existent component.
- **Parallax reuses the Lenis null-fallback pattern (FR-006), not necessarily the hook body.** `useScrollProgress` returns a 0→1 section-through-viewport progress value — parallax needs an absolute-scroll-delta / element-relative offset instead. Reuse the *pattern* from `use-scroll-progress.ts:59-81` verbatim (Lenis `.on("scroll", …)` branch when `useLenis()` is non-null, passive native `scroll` listener fallback when null, rAF-coalesced, full cleanup on unmount) inside a new `use-parallax-offset.ts`. If the executor can cleanly generalize `useScrollProgress` to serve both, that also satisfies FR-002's no-orphan rule; if not, delete `use-scroll-progress.ts` when the last gallery consumer goes. Decide in Wave 2a, document which path was taken.
- **Parallax must compose with `.animate-mockup-float`, not fight it (FR-007, edge case spec line 58).** `Hero.tsx:57` puts `.animate-mockup-float` (a CSS `@keyframes mockup-float` `translateY` loop, `globals.css:296-298,330-331`) on the mockup's wrapper div. An inline `transform: translateY(...)` on the SAME element would override the keyframe animation (the CSS `transform` property and the `animation`'s `transform` don't compose on one node). Solution: apply the parallax `translateY` to a SEPARATE wrapper element (an outer `HeroParallax` div around the existing `.animate-mockup-float` div), so the two transforms live on different nodes and stack naturally. Never merge them onto one element.
- **Gates are the single source of truth for reduced-motion/desktop (FR-005).** `useIsDesktop()` (768px `md:` query, `lib/motion/use-is-desktop.ts`) and `useMotionGate()` (`{ prefersReducedMotion, isDesktop }`, `lib/motion/motion-gate-context.ts`) already exist and are consumed by `ScrollAwareNav`, `ScrollProgress`, and (until Wave 1) `ValueGalleryMotion`. The new parallax MUST gate on these, not introduce a duplicate `matchMedia` check. On live resize across 768px, follow the established convention: apply NO inline transform in the inactive branch (leaving the key out entirely, matching the pattern documented in `ValueGalleryMotion.tsx:69-82`) so there is no stuck offset.
- **Stagger extends `SectionReveal`'s non-replay guarantee (FR-008/FR-009), does not duplicate it.** `SectionReveal.tsx` reveals its whole children block as one unit via a single `IntersectionObserver` that `observer.disconnect()`s after the first `isIntersecting` (lines 55-63), and renders a plain `<div>{children}</div>` with no reveal class at all under `prefersReducedMotion` (lines 71-73). Per-child stagger is a NEW capability — a `StaggerReveal` wrapper (or a `staggerIndex`/`transition-delay` extension) composed WITH `SectionReveal` — that must reuse the same single-fire observer and the same reduced-motion plain-render branch, so the "appear immediately, no stagger, no replay" fallback (FR-009, US-002-4) is preserved for free rather than re-implemented.
- **PricingSection has TWO grid containers, not one flat row (spec line 184).** `PricingSection.tsx` renders the Enterprise anchor (`div.card-glass`, lines 36-68) and the three Starter/Team/Pro tiers (`.map()` over `SELF_SERVICE`, lines 71-124) inside a two-column outer grid (`lg:grid-cols-[1.1fr_2fr]`, line 34), with the tiers in their own nested `grid sm:grid-cols-3` (line 71). The stagger implementation must account for this split — either stagger anchor-then-tiers as a 4-item logical sequence, or stagger the tiers only — NOT assume four uniform siblings in one grid. Decide in Wave 2b and document.
- **Stagger uses CSS transitions, not JS animation (FR-008).** Follow the existing `.section-reveal` pattern (`globals.css:613-623` — `opacity`/`translateY` transition, `[data-revealed="true"]` end state, transform/opacity only → zero CLS). The per-child stagger adds `transition-delay` per card (approx. 100ms × index) plus a `scale` (0.97→1) to the same transition, driven by a data attribute / CSS class, not `requestAnimationFrame`.
- **No new npm dependencies, no test framework install.** Spec keeps automated animation/visual-regression tests Out of Scope (spec line 154); manual QA is the declared acceptance method, consistent with 001. Wave 3 is a manual-QA-checklist + green-build wave mapped to SC-001…SC-006, NOT a Vitest/Playwright install. The 001 QA doc (`docs/qa/lenis-smooth-scroll-qa.md`) is the format template for the new `docs/qa/scroll-motion-redesign-qa.md`.
- **Per-wave infrastructure lines:** every wave below declares DB / RLS / ENV / restart explicitly. For this feature all four are **none** on every wave — pure client-side presentational changes, no schema, no row-level-security, no environment variables, no service restart. Stated per wave so the gates see it, not left implicit.

## Wave 2a — Hero parallax  ⟶ status: pending  ⟶ status: done

**Goal:** A desktop-only, reduced-motion-gated, Lenis-driven vertical parallax drift is live on the Hero dashboard mockup, composing with — not overriding — its existing float animation, and the Wave-1-deferred `use-scroll-progress.ts` orphan is resolved (reused-and-generalized or deleted, no dead hook survives).

**Depends on:** Wave 1 (finalizes the `use-scroll-progress.ts` reuse-vs-delete decision Wave 1 left pending)
**Parallelizable:** yes — independent of Wave 2b (stagger); the two touch disjoint files (2a: `Hero.tsx`, `HeroParallax.tsx`, `use-parallax-offset.ts`, `use-scroll-progress.ts`; 2b: `ValueSection.tsx`, `PricingSection.tsx`, `StaggerReveal.tsx`, `globals.css`) and can run concurrently after Wave 1
**FRs covered:** FR-004, FR-005, FR-006, FR-007

**Stories advanced:** US-002-2 (hero parallax drift), US-002-4 (reduced-motion / mobile parity — parallax half)

**DB:** none · **RLS:** none · **ENV:** none · **Restart:** none (client-side motion components; `pnpm build` is the only gate)

### Brief for code agents

- Create `components/motion/HeroParallax.tsx` (client) — an outer wrapper the Hero renders AROUND the existing `.animate-mockup-float` div (`Hero.tsx:57`). Apply the parallax `translateY` to THIS outer wrapper only, never to the float div, so the keyframe float and the scroll parallax live on separate nodes and compose (FR-007). Optionally also drift the hero background glow (`Hero.tsx:19-26`) as a second, subtler parallax layer — allowed by FR-004 ("and optionally the hero's background gradient glow"), not required.
- Create `lib/motion/use-parallax-offset.ts` (client) — returns the vertical parallax offset in px. Drive it from `useLenis()` with the SAME null-fallback pattern as `use-scroll-progress.ts:59-81` (Lenis `.on("scroll")` when non-null, passive native `scroll` listener when null, rAF-coalesced, full cleanup). Map scroll position to a `translateY` at approx. 0.85× native rate, total accumulated drift clamped to ~40–60px (FR-004). Do NOT assume a non-null Lenis instance (FR-006).
- **Resolve the Wave-1 orphan (completes the no-orphan intent of Wave 1's deletion):** decide now whether `use-parallax-offset.ts` generalizes/absorbs `use-scroll-progress.ts` (then delete the old file and update its header comment) or is a distinct hook (then DELETE the now-consumerless `use-scroll-progress.ts` — no orphan may survive). Record the choice in the commit message. (The no-dead-code requirement itself is a Wave 1 coverage item and is verified there; this is the follow-through the orphan-resolution note in Wave 1 points to.)
- Gate the parallax on `useMotionGate()` + `useIsDesktop()` (768px), NOT a new `matchMedia` (FR-005). Under `prefers-reduced-motion: reduce` OR viewport <768px, apply NO inline transform on the wrapper (leave the key out entirely, per the `ValueGalleryMotion.tsx:69-82` convention as it read pre-Wave-1) so there is no stuck offset on resize across the breakpoint (edge cases spec lines 143–144).
- Handle the `eager`-revealed Hero correctly (edge case spec line 142): the parallax offset calculation reads live scroll position and must not assume the Hero went through a non-eager IntersectionObserver reveal cycle.
- Mount `HeroParallax` inside `Hero.tsx` (server component stays server; the new client wrapper is composed around the mockup, mirroring the 001 wrap-don't-convert pattern).
- transform/opacity-only, zero CLS; never touch `pointer-events` or focus so CTAs stay clickable/Tab-focusable (the cross-cutting regression guarantee — see the coverage matrix — is verified in Wave 3). Verify `pnpm build` green.

### Behavioral acceptance (one AC per FR)

- **FR-004:** On desktop with default motion settings, scrolling past the Hero drifts `HeroDashboardMockup` (and optionally the background glow) vertically at ~0.85× native scroll rate via transform-only `translateY`, total accumulated drift capped at ~40–60px.
- **FR-005:** The hero parallax is active on viewports ≥768px only and is disabled entirely under `prefers-reduced-motion: reduce`.
- **FR-006:** The hero parallax is driven by the same `useLenis()` scroll signal used elsewhere, with the established null-instance fallback (passive native `scroll` listener when Lenis is unavailable) rather than assuming a non-null instance.
- **FR-007:** The hero parallax `translateY` composes with the mockup's existing `.animate-mockup-float` keyframe animation without overriding it — the two transforms apply on separate wrapper elements, not one conflicting inline `transform`.

Prefer a new thin `components/motion/StaggerReveal.tsx` client wrapper (or a `staggerIndex`/`transition-delay` extension of `SectionReveal`) that reuses `SectionReveal`'s single-fire `IntersectionObserver` (disconnect-after-first, `SectionReveal.tsx:55-63`) and its reduced-motion plain-render branch (`SectionReveal.tsx:71-73`) — do not duplicate the observer or the reduced-motion check (FR-009).
