## Relevant Codebase Patterns

### Current merge-check flow (`pr-merge-check.cjs` `mergeCheck`, l.211-262)
`resolveBaseRef` -> `resolveMergeBase` -> `guardReasons` (HEAD==PR head on clean tree, committed dispositions, self-review, config change) -> `ciDecision` (decided before any run: FR-017 first half already true) -> `headMoved` TOCTOU re-read of `gh pr view` (only on the CI-evidence path) -> `runVerify({project, base, noCache: true})` in process -> `requiredChecks` -> reasons list -> report. `setRecordExtra({ci_evidence_why})` after.

### Current `runVerify` order (`verify-run.cjs` l.496-545) - the thing FR-011 reverses
1. `baseConfigGuard`/`selectBasePlan` pick the command set from the BASE (merge-base) `.a1/verify.json` (SEC-2: PR cannot choose what judges it).
2. `runBaseSide` runs EVERY base command first in a `git archive` snapshot (`vb.withSnapshot`), producing `ids` (failing-id sets), `skipped`, `durations`.
3. `runHeadSide` runs every head command in a head snapshot (`withSnapshot(project, head, runHead, 'head')`), settling each command inline: `vb.settle(first, retry, baseIds, flakyBase)`. The retry decision (`isRetryable`) already depends on `baseIds` (retry only when a failing id is not red on base).
4. `applySkipIncrease(side.settled, base.skipped, ...)` compares skipped counts against base (this is why FR-011 keeps base for counting reporters).
5. `hostLib.applyEnvRed(..., sel.compareBase, opts.base !== undefined)` - env_red under --base excuses only ids red on base AND head (red on head => base runs under lazy rule, so unchanged).
All commands run sequentially via `runCommand` -> `spawnGroup` (`spawnSync` of a node group-runner child, SIGKILL of the process group on every exit, `commandReason` maps `timed_out` -> `timeout`).

### FR-011 consequences (concrete)
- `settle` needs `baseIds` BEFORE the retry; `runHeadSide` settles inline. Restructure: run all head commands raw (first run), collect red set R, run base only for R plus every command with a counting reporter (kind != `none`), then settle per command (retry after). For green+`none` commands `baseIds` is irrelevant (`reason === null`, no retry).
- A lazy base means no `runBaseSide` call at all when R is empty and no counting reporter: base snapshot (`git archive` + node_modules copy) must also be skipped. `withSnapshot` is called inside `runBaseSide`, so lazy skipping is natural; but `base` object is used downstream (`base.ids`, `base.skipped`, `base.durations`, `base.cache`, `baseMs`) - all consumers need a "no base run" shape (`cache.base`, `base_duration_ms: null`, `duration_ms.base: null` already allowed by the record).
- `suite_removed`/`config_changed`/`flaky_base_grown` do not depend on running base commands (they use git objects), so they stay.
- No spawn-counting seam exists today (grep: `verify-run.cjs` has no `process.env.A1_*` seam). The spec's fixture ("counted through a spawn seam") needs a new seam, e.g. a module-level injectable `spawnGroup` or an env-var-named counter file; name it in the plan. Cache is off under merge-check (`noCache: true`), so counts are exact.
- Risk: report-shape consumers. `pr-merge-check` report reads `record.pre_existing_red`, `record.cache`, `record.skipped_on_host`; `verify check`/`verify reuse` read the record; existing `a1-verify` asserts cover base ordering and cache fields (`cases-durations.sh`). The FR-012 evidence is "existing suites pass + zero deleted assert lines" (numstat check is NEW).

### Runner contract today (`bin/run-suites.sh`, measured)
- Options: `--workers`, `--job`, `--extra-job`, `--locale-native`, `--check-groups`, `--root`, selectors (a selector with `/` is a suite identity such as `a1-intent/run-tests.sh`; one without is a directory). Selector selecting nothing exits 2 before lock/workdir.
- NOT present: `--json-out`, `--lock-wait`, per-suite watchdog, retry, a groups-file option. (`grep json-out|lock-wait|watchdog bin/*.sh`: only a comment hit.)
- Exit codes: 0 green, 1 a suite or leak/reconcile/learnings/phases check failed, 2 usage/config (nothing started) - `rs_lock_acquire` also returns 2 when "another run holds the lock" (fail-fast, 8 attempts only for takeover races, no waiting).
- Per-suite isolation: `rs_spawn_worker` runs `env -u A1_VAULT_WRITER_HOST -u A1_SUITE_REAL_VAULT A1_HOST_ID=leak A1_VAULT_ROOT=<empty sentinel> HOME=<fresh dir> bash _test-fixtures/<id>` in its own process group (`set -m`), `cd "$RS_ROOT"`. Env is otherwise inherited, so `A1_VERIFY_LOCK_TOKEN` (FR-018) passes through to nested `verify run` without change, as the spec requires. `LC_ALL=C` exported unless `--locale-native`.
- Leak notes: `rs_on_suite_done` prints `leaked: <path>` lines and a `note`; a non-empty note makes `RS_FAILED=1` (`rs_main` tail). These are the data for FR-013 `leak_note`. Post-run checks (reconcile, learnings, phases) are skipped with named lines when `$RS_ROOT` is not a git top-level (`nogit`) - exactly the "snapshot run" FR-016 must name.
- Run lock: fixed `/tmp/a1-suite-runner-<uid>` (seam `A1_SUITE_LOCK_DIR`), holder judged live by PID alive AND `ps -o command=` containing `run-suites.sh` (PID-reuse guard). A base-sourced runner copy must keep the file name `run-suites.sh`, or the liveness test treats its own lock as stale.
- The runner reads `$RS_ROOT/_test-fixtures/suite-groups.json` (`rs_load_groups`) and discovers suites by globbing `$RS_ROOT/_test-fixtures/*/run*.sh`. With `--root <head snapshot>` the declaration file therefore comes from the HEAD snapshot even when the script comes from base. FR-014 forbids that (spec names `suite-groups.json` among the files that must come from base). A runner option to read groups from the runner's own tree (`--groups-file`/default to `$RS_BIN_DIR/../_test-fixtures/suite-groups.json`) is needed, and it is not in FR-013..FR-016's list - a plan decision, not a product one. `serial`, `no_count` and `timings` are the groups-file fields that matter (ordering, serial group, pass counting).
- Timings (suite-groups.json): 62 suites, sum 1268 s, max 285 s (`ci_job_workers` only sets fixtures-xprov to 3). Default workers = cores-2 clamped 1..6.

### Mapping command ids to runner identities
`.a1/verify.json` uses `each: "_test-fixtures/*/run*.sh"` plus one explicit `commands` entry (`_test-fixtures/a1-schema-check/parser/run-parser.sh`, which the runner lists under `no_count`). Command id = `_test-fixtures/<identity>`; identity = id minus the `_test-fixtures/` prefix (spec FR-013). Long-path eligibility must be explicit: every command must have argv exactly `bash <id>`, reporter `none`, and an id under `_test-fixtures/` that the runner would discover; anything else (counting reporter, `requires_host`, npm commands in a customer project) falls back to the sequential `runVerify`. The spec only names the base-copy-missing fallback (FR-014); eligibility is an additional planner rule I recommend, not a decision for the owner. Also: this `.a1/verify.json` is a1-specforge-specific; other repos keep the sequential path.

## Recommendations

1. Deliver in the spec's order and keep each step independently green: (a) lazy base in `runVerify` incl. spawn seam and the "no base ran" record shape; (b) runner contract (`--json-out`, `--lock-wait`, groups-file option, watchdog) with its own `a1-suite-runner` cases; (c) base-sourced runner + eligibility + sequential fallback; (d) retry-after-base ordering and env-equality check; (e) `verify-lock.cjs`, token, lint rule, workflow text. Extract the long path into its own module to stay under the 800-line cap.
2. Treat the runner as a untrusted-input boundary on both sides: script and groups file from base, result only via the validated JSON file in a verify-run-owned temp dir, requested-vs-returned set compared, runner exit 2 mapped to merge-check exit 2 with the reason passed through, never red or green.
3. Keep `settle`, `NEVER_PRE_EXISTING` and `commandReason` untouched in behaviour; reorder only the callers. Prove FR-012 with the numstat script plus all new fixtures as NEW `cases-*.sh` files (no edits to existing asserts).
4. Re-measure which suites really execute `verify run` before wiring `A1_VERIFY_LOCK_TOKEN`; add a nested-run fixture on the real tree, and add the token to the allowed env in both `SUITE_ENV_DROP` handling and the runner environment (keep it, never drop it).
5. Plan the verification for the slice's own merge-check: it edits `bin/run-suites*.sh` (under `ci_evidence.unchanged`), so it runs the slow serial path once (~50 min, measured); schedule it once, after Samuel's fixes, and add a measured long-path row afterwards (second baseline) with `host_load`.
